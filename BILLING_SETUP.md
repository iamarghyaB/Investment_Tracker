The app uses Supabase project `xyltxzqmtoqnmwpfkmnf` (InvestmentTracker), created in Makezaastdio.inc, Singapore. Its URL and public key are configured. The schema has been applied and verified with rollback-only two-user RLS fixtures.

## Local keys

Fill these fields in ignored `.env.local`; never put actual values in source files or chat.

- `SUPABASE_SECRET_KEY`: server-only secret from the new project's API Keys page (normally `sb_secret_`). Billing customer registration and verified webhook writes need it.
- `STRIPE_SECRET_KEY`: sandbox restricted key (`rk_test_` preferred) or sandbox secret key (`sk_test_`). Live keys are explicitly rejected.
- `STRIPE_PRICE_ID`: generated by the setup script below.
- `STRIPE_WEBHOOK_SECRET`: generated by the listener script below.
- `NEXT_PUBLIC_APP_URL`: `http://127.0.0.1:3000`. Keep this consistent with the browser URL and auth redirect settings.

A restricted Stripe key needs appropriate access to Customers, Products, Prices, Checkout Sessions, Subscriptions (read), and Billing Portal configurations/sessions. If the restricted key cannot start the CLI listener, authenticate the CLI in the same sandbox separately or use a sandbox test secret for local development.

## Provision and test

1. Run `node scripts/setup-stripe.mjs`. It creates/reuses an idempotent sandbox product and **$20 USD/month** price, saves `STRIPE_PRICE_ID`, and prepares a portal configuration when no default exists.
2. In another terminal, run `node scripts/listen-stripe.mjs`. It saves the webhook signing secret without printing it and forwards the required events to the local app. Keep it running during testing.
3. Restart the Next.js dev server after environment changes.
4. Create an account at `/login`, confirm its email, and sign in. Open `/pricing` and choose **Try Pro in sandbox**.
5. Complete Stripe-hosted checkout with a test card such as `4242 4242 4242 4242`, a future expiry, and a test CVC. Do not enter a real card in sandbox testing.
6. The signed webhook activates Pro. Return to the dashboard, search a supported stock, save it with the star, and refresh to verify persistence.
7. Use **Manage subscription** to cancel. Access remains until the paid period ends for scheduled cancellations; users can still read/remove prior saved stocks afterward, but cannot add new ones.

## Supabase auth redirects

In Authentication → URL Configuration, set Site URL to `http://127.0.0.1:3000` and allow `http://127.0.0.1:3000/auth/callback`.

The callback exchanges the PKCE code for a session. With Supabase's default localhost redirect, email confirmation still allows manual sign-in afterward, but auto-login may not work across the differing cookie hostnames. Keep email confirmation enabled.

## Security and verification

- Watchlist SELECT/DELETE require the authenticated user's ownership. INSERT also requires an active, unexpired subscription.
- Authenticated users cannot modify subscriptions or call privileged billing sync.
- Signed raw-body webhooks reject live events, validate the price, map customer ownership on the server, and retrieve the current Stripe subscription before syncing.
- Database event deduplication and ordering protect against webhook replays and older events.
- Checkout return parameters never grant access. All browser billing routes require a verified user and matching request origin.
- `database/verify_rls.sql` verifies account isolation, write denial, paid gating, expiry, billing replay/order handling, and anonymous denial; all test fixtures are rolled back.
- Supabase's security advisor reported no findings after applying the schema.
